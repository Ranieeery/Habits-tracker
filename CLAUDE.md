# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working in this repository.

## Project

Habit tracker with a GitHub-contribution-style heatmap. Single real user (the owner), but built so that multi-user is possible later (every row is scoped by `user_id`). **Mobile-first**; the web client is a secondary, fully functional PWA.

This repository is a rewrite of a legacy app that lived as three independent npm projects (Fastify + Prisma/SQLite, React + Vite, Expo). The legacy code was removed from the tree after the v2 deploy; it remains in git history as a **read-only behavioral reference** at the tag `v2.0.0` (commit `5ce71d4`, the last one with `legacy/`): read it with `git show v2.0.0:legacy/<path>` or `git ls-tree -r --name-only v2.0.0 -- legacy/`. Never restore or import it.

Version: this rewrite is **2.0.0** in all three apps: api, web and mobile (see "Git and versioning").

### Product scope

Existing features to preserve:

- Create habits that recur on chosen weekdays (Sunday = 0 ... Saturday = 6).
- Mark a habit as done/undone for a day; a day's completion ratio drives the heatmap intensity.
- Year-to-date heatmap grid, and a per-day view listing possible/completed habits.
- UI text in Portuguese (pt-BR), dayjs locale `pt-br`.

New features:

1. Authentication and authorization (single-owner; public signup disabled after the first account).
2. Push notifications: Expo push on mobile, Web Push + service worker on the web.
3. Offline-first on mobile with background sync (delivered last, but the data model must support it from day one).
4. Clean UI, keeping the existing color palette fully or partially (see Design).

The product must stay **extensible**: new habit types/frequencies, new stats, new notification kinds. Prefer discriminated unions and versioned contracts over hardcoded assumptions.

## Repository layout

pnpm workspaces + Turborepo monorepo. Run commands from the repo root with `pnpm --filter <name>` unless a command says otherwise.

- `apps/api/` — Hono on Cloudflare Workers, D1 (SQLite) via Drizzle. The single backend service (the "monolith").
- `apps/web/` — Vite + React 19 PWA, deployed as the public Worker `habits` (static assets + `/api` gateway to the API).
- `apps/mobile/` — Expo (latest stable SDK) + Expo Router. Primary client.
- `packages/contracts/` — Zod schemas and inferred types for every API request/response, plus sync protocol types. Single source of truth.
- `packages/core/` — pure TypeScript domain logic: date handling, schedule evaluation ("is this habit possible on this date?"), completion ratios, streaks, heatmap grid generation. No I/O, no framework imports. Fully unit-tested.
- `packages/api-client/` — typed client for the API (Hono RPC `hc` over the `AppType` declarations emitted by `apps/api`), shared by web and mobile.
- `packages/design-tokens/` — colors, spacing, radii extracted from the legacy palette; consumed by Tailwind (web) and NativeWind (mobile).
- `.github/` — GitHub Actions (`checks`, `ci`, `deploy`, `backup`) and Dependabot (actions only). See "Decisions" (Phase 8) and the runbook in `README.md`.

Formatting and linting are shared from the root: `.editorconfig` (tabs, width 2, LF; spaces only for YAML and Markdown), Prettier (`useTabs: true`, `tabWidth: 2`, double quotes, semicolons, `trailingComma: "es5"`, LF) and ESLint. Keep `.editorconfig` and the Prettier config consistent with each other; if they ever conflict, Prettier's config wins for code. TypeScript is `strict` everywhere.

## Architecture

### Domain model (D1 / Drizzle, `apps/api/src/db/schema.ts`)

All tables carry `user_id`, `created_at`, `updated_at`; syncable tables also carry `deleted_at` (tombstone). IDs are client-generatable UUIDs (v7) stored as text so offline clients can create records.

- `habits`: `id`, `user_id`, `name`, `schedule` (JSON, discriminated union validated by `contracts`; today only `{ type: "weekdays", days: number[] }`), `start_date` (date), `archived_at`.
- `completions`: `id`, `user_id`, `habit_id`, `date` (`YYYY-MM-DD`), `completed_at`, `deleted_at`. Unique on `(habit_id, date)`. A row means "done"; un-checking sets `deleted_at` so the change can sync.
- `user_settings`: PK `user_id`, `timezone` (default `America/Sao_Paulo`), `reminder_time` (`HH:MM`, null = off). More notification preferences are added as columns when needed.
- `push_subscriptions`: `kind` (`webpush` | `expo`), `endpoint`/`p256dh`/`auth` or Expo `token` (a CHECK enforces the fields per kind), `device_label`, `last_seen_at`. Not syncable: hard delete.
- `reminder_state` (server-only, not a contract record, not synced): PK `user_id`, `last_reminder_date` (`YYYY-MM-DD`, claimed before sending), `last_test_push_at` (rate limit of the test push), `updated_at`. Kept out of `user_settings` so that row stays exactly the `UserSettings` record.
- `push_tickets` (server-only): Expo push tickets waiting for their receipt (`id` = receipt id, `user_id`, `subscription_id` with cascade, `created_at`).
- Sync bookkeeping (server-only, Phase 7): `habits.server_seq` and `completions.server_seq` (the row's position in the user's change feed, set by SQLite triggers on every insert/update, never by app code, dropped when reading records), `sync_state` (PK `user_id`, `seq` = last seq given, `purged_seq` = highest seq among purged tombstones) and `processed_mutations` (PK `(user_id, mutation_id)`, `canonical_id`, `processed_at`; applied mutations only).
- Auth tables (`user`, `session`, `account`, `verification`, `rate_limit`) are owned by Better Auth and generated by its CLI into `apps/api/src/db/auth-schema.ts`. User ids are UUIDs (`crypto.randomUUID()`).

The database row of every table, minus `user_id` (and `server_seq`), is exactly the contract record (`Habit`, `Completion`, `UserSettings`; `PushSubscription` is stored flat): `apps/api/test/rows.test.ts` asserts this at type level. Writes go through `apps/api/src/db/records.ts`, which parses with the contract first (the DB CHECK on `schedule` only requires JSON with a string `type`, so new schedule types need no migration).

Every `user_id` references `user.id` with `ON DELETE CASCADE` (added in `0002_user_fk.sql` by a table rebuild with `PRAGMA defer_foreign_keys = on`, since D1 always enforces FKs and ignores `PRAGMA foreign_keys`). Deleting a user deletes all their data. The dev seed creates the auth user with the fixed `DEV_USER_ID` and a password credential in the same batch as the data.

Differences from the legacy model (intentional):

- No `Day` / `DayHabit` tables; a single `completions` table replaces them.
- Calendar dates are **local calendar dates as `YYYY-MM-DD` text**, never epoch milliseconds (instants like `created_at` are UTC ms; see "Decisions"). This removes the legacy `strftime` weekday workaround and timezone bugs. The weekday is derived in `packages/core`, not in SQL.
- "Possible on date D" = habit not archived-before-D, `start_date <= D`, and the schedule matches D. This logic lives only in `packages/core` (`isHabitPossibleOn(habit, date, { timeZone })`; the time zone turns the `archived_at` instant into a local date, and a habit archived during D still counts on D) and is reused by API and both clients. `core` never reads the clock: callers get today with `todayIn(timeZone, nowMs)`.

### API (`apps/api`)

- Routes are defined with `@hono/zod-openapi` using schemas from `packages/contracts`; OpenAPI docs are served at `/v1/docs` (and JSON at `/v1/docs/json`) only when `ENVIRONMENT=development`. Do not duplicate Zod schemas inside handlers. Errors use `ApiError` from contracts (validation failures are 422 `validation_error`); only `/v1/auth/*` (Better Auth) answers in Better Auth's own format.
- Routes: `GET/POST /v1/habits`, `PATCH /v1/habits/{habit_id}` (rename, reschedule, archive/unarchive), `PUT /v1/habits/{habit_id}/completions/{date}` (`{ completed, id? }`, idempotent, undo writes a tombstone), `GET /v1/day?date=`, `GET /v1/summary?year=`, `GET/PATCH /v1/settings`, `POST /v1/push/subscriptions` (upsert by endpoint/token), `DELETE /v1/push/subscriptions/{subscription_id}`, `POST /v1/push/test` (sends a test notification to all the user's devices; one per minute, 429 `rate_limited` with `Retry-After`; answers `{ sent, failed, removed }`), `POST /v1/sync/push`, `GET /v1/sync/pull?cursor=&limit=` (see "Offline sync"). Push responses never include the endpoint, keys or token.
- The current instant is injected (`createApp({ now })`; `src/index.ts` is the only place that reads `Date.now()`), and a user's day is always `todayIn(user_settings.timezone, now())`.
- All routes are under `/v1`. Keep changes backward compatible (expand/contract): old mobile builds and queued offline mutations may hit a newer API.
- Date writes: the client sends the local date explicitly. The server accepts dates in `[today - BACKFILL_DAYS, today + 1]` relative to the user's timezone. `BACKFILL_DAYS` is a constant in `packages/core` (default 7, to allow offline sync). Legacy behavior was "today only"; do not widen the editing UI without being asked.
- D1 has no interactive transactions; use `db.batch([...])` for multi-statement atomicity. Limits (Free): 100 bound parameters per statement (Drizzle binds every column of a multi-row insert, defaults included: chunk with `columnCount`), 100 KB per statement, and **50 queries per invocation** (1000 on Paid). The docs do not say whether each statement of a batch counts, so budgets assume it does.
- Summary/heatmap data loads the year's live completions and the habits (one query each) and counts each day with `core` (`summarizeDay`), so "possible" and completed counts follow the same rules as the clients.
- A Cron Trigger every 15 minutes (`*/15 * * * *`, UTC) runs the reminder job with its scheduled time as "now" (see "Push notifications").
- Every API response (Better Auth's included) carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff` (`src/http/api-headers.ts`); the web's `_headers` file only reaches static assets. Logs go through `src/lib/log.ts` as JSON objects `{ event, ...fields }` with counts, statuses, codes and error names only: never emails, cookies, tokens, push endpoints or keys, bodies or URLs with query strings.

### Auth

Better Auth with the Drizzle adapter on D1, mounted at `/v1/auth/*` and built per request (`apps/api/src/auth/auth.ts`). Email + password (passkey can be added later), minimum 16 characters. Signup is open only while no user exists (optionally only for `OWNER_EMAIL`); `ALLOW_SIGNUP=true` reopens it in development. Web uses cookie sessions (`HttpOnly`, `SameSite=Lax`, `Secure` with the `__Secure-` prefix outside development); mobile uses the Expo plugin (`expo()`) and/or bearer tokens (`bearer()`, token from the `set-auth-token` header) stored with `expo-secure-store`. Sign-in and sign-up are rate limited in the database (`rate_limit` table, keyed by `cf-connecting-ip`). CORS and trusted origins come from `TRUSTED_ORIGINS` (empty in production) plus the `habits://` app scheme.

Every query must filter by the authenticated `user_id`: `requireUser` guards every non-public route, and handlers only use `src/repos/*`, whose functions all take `userId` and scope every statement by it (the one cross-user statement moves a push device, proven by its endpoint/token, to the user who registers it). Never rely only on the client.

How the owner account comes to exist: in production, the owner signs up once (`POST /v1/auth/sign-up/email`) right after the first deploy, with `OWNER_EMAIL` set so nobody else can take the slot; afterwards signup answers 403 `SIGNUP_DISABLED`. In development, `db:seed:local` creates it.

### Push notifications

- Mobile: Expo Push Service from the Worker (`apps/api/src/push/expo.ts`, plain fetch); tokens registered via `POST /v1/push/subscriptions`. `DeviceNotRegistered` (in the ticket, or in the receipt read by a cron run at least 15 minutes later) removes the device; tickets without a receipt are dropped after 24 h.
- Web: standard Web Push with VAPID, our own Web Crypto implementation (`apps/api/src/push/webpush.ts`: RFC 8291 `aes128gcm` + RFC 8292 ES256 JWT, tested against the RFC 8291 Appendix A vector). The VAPID private key and subject are Wrangler secrets, never committed; the public key is also `VITE_VAPID_PUBLIC_KEY` in the web build.
- iOS web push only works for the installed PWA (Add to Home Screen).
- Remove subscriptions on 404/410 responses (Web Push) and `DeviceNotRegistered` (Expo); other failures (429, 5xx, network) keep the device. One device failing never stops the others.
- Reminders: the pure decision is `shouldSendReminder` in `packages/core` (after `reminder_time` in the user's zone, pending habits today, at most one per local day, off when `reminder_time` is null). The job claims the day in `reminder_state` with a conditional upsert **before** sending, so overlapping or repeated runs send at most once (a failed send loses that day's reminder). Text: "Você tem N hábito(s) pendente(s) hoje." (counts only, never habit names). A tap opens today (`/today` on web, `/day/hoje` on mobile).
- Limits (Workers Free): at most 40 push fetches per invocation (limit 50); users who do not fit are not claimed and go to the next run. Web Push costs about 1 ms of CPU per device (local workerd), Expo is one fetch per 100 tokens.
- Permission is asked only when the user turns reminders on in Settings, never at launch. `reminder_time` is per account; permission and registration are per device.
- Reminders and offline changes: the server decides the reminder with the data it has. Completions made offline and not yet synced do not count, so the phone may get an unnecessary reminder ("pendente" for a habit already marked). Known and accepted; not solved for now (a sync just before `reminder_time`, which the foreground and background triggers often do, avoids it).

### Offline sync (mobile, Phase 7)

Local-first storage in `expo-sqlite` on mobile; the web stays online-only. Rules shared by API and app live in `packages/core/src/sync.ts` (`applyMutation`, `materialize`, `orderOutbox`, `blockedBy`, `remapIds`); contracts in `packages/contracts/src/sync.ts` (protocol version 1).

- **Mutations**: `habit.create` (`id`, `name`, `schedule`, `start_date`), `habit.update` (`habit_id`, `changes` = `UpdateHabitRequest`, only the fields it carries are written), `completion.set` (`id` proposed, `habit_id`, `date`, `completed`). Each has a client `mutation_id` (UUID v7) and `created_at` (informative). They mirror the REST writes, and REST uses the same core functions.
- **`POST /v1/sync/push`** (`{ protocol, mutations }`, at most `SYNC_PUSH_MAX_MUTATIONS` = 100; the app sends 50): the envelope only checks `mutation_id`s, each mutation is parsed alone, so an invalid one (or an unknown type from a newer app) is rejected alone. Applied in array order over the user's records loaded in memory, then written in **one `db.batch`** with chunked multi-row statements (worst case about 30 statements). One result per mutation: `applied` (+ `canonical_id`), `duplicate` (`mutation_id` already in `processed_mutations`, nothing written, same `canonical_id`) or `rejected` (+ `error`, permanent). Only applied mutations are recorded, so a retry of a rejected one is evaluated again. The insert into `processed_mutations` is a plain INSERT in the same batch: a concurrent duplicate of the same push aborts as a whole (500, transient) and its retry answers `duplicate`.
- **Rejections** (permanent): unknown, deleted or another user's habit = `not_found` (indistinguishable); `habit.create` with an id another user has = `conflict`; `start_date` before `today - BACKFILL_DAYS` or a completion date outside `[today - BACKFILL_DAYS, today + 1]` (user's time zone, injected clock) = `date_out_of_range`; bad shape = `validation_error`. A completion whose proposed id is taken by another record gets a fresh server id (`canonical_id`), not an error. Completions of archived habits are accepted, like REST.
- **Cursor**: `server_seq`, a per-user counter shared by both tables (`sync_state.seq`), assigned by SQLite triggers (migration `0004_sync`) to every inserted or updated row, whatever wrote it (REST, sync, seed). Each row gets a unique value even within one statement or millisecond; D1 serializes writes and a batch is a transaction, so commit order is seq order. `GET /v1/sync/pull?cursor=&limit=` (default 200, max 500) reads both tables **in one batch** (a consistent snapshot: two separate reads could skip a row committed in between), merges by seq and returns the cursor of the last row delivered (opaque `1.<seq>`), `has_more`, `remaining` (progress) and records with tombstones. A row changed again comes back with its newer state; nothing is skipped or repeated within one state. `updated_at` is informative only.
- **Conflicts**: last write wins in the order the server applies writes (arrival order; final tie-break = `server_seq`), never by device clocks: the server stamps `created_at`/`updated_at`/`completed_at`/`archived_at`/`deleted_at` with its own instant. The device that syncs last wins, even if its edit was made earlier offline. Habits merge per field. Completions are unique per `(habit_id, date)`: the push upserts on that key, the first stored id stays, and the result's `canonical_id` lets the app rewrite its local id. Unchecking writes a tombstone (also when no row existed); checking a tombstone again revives it with the same id.
- **Wrong device clock**: does not affect order or stored instants. It changes the device's "today", so the date written: more than 1 day ahead or 7 behind is rejected (`date_out_of_range`, shown in the failures list); inside the window the completion lands on the wrong day (undetectable). The app compares each response's `Date` header with its clock and warns when they differ by more than 5 minutes.
- **Retention**: `TOMBSTONE_RETENTION_DAYS` = `PROCESSED_MUTATION_RETENTION_DAYS` = 90 (core). The cron's first run after 06:00 UTC purges, user by user (at most 8 per run, one batch each): raises `purged_seq`, deletes old completion tombstones, deleted habits (and their completions) and old `processed_mutations`. A pull with a cursor below `purged_seq` (device offline for more than 90 days), above `seq` (restored database) or unreadable answers `reset: true`: the app drops its mirror, keeps its outbox and pulls everything again. Residual risk: an applied mutation whose response was lost and that is resent only after 90 days would apply again.
- **App storage** (`apps/mobile/src/data/local/`): `habits` and `completions` mirror the server (written only by pulls); user changes go only to the `outbox` (one local transaction) and screens read `materialize(mirror, outbox)`, the pending and applied mutations replayed over the mirror. A rejected mutation stops being replayed, so the screen goes back to the server state on its own, and the change stays in the failures list until retried or discarded. Applied entries are kept (and replayed) until the next full pull brings the server's version. Settings are read from a local copy refreshed by each sync; changing them still needs the network.
- **App engine** (`apps/mobile/src/data/sync/`): push (dependency order: a `habit.create` before the changes of that habit; changes of a habit whose creation failed are not sent and fail as `dependency_failed`, grouped with it), then pull page by page (cursor written in the page's transaction: an interrupted pull resumes, a resent push answers `duplicate`), then settings. One run at a time: in-memory lock plus a 60 s lease in the database for the background task's JS context. Failures: offline (network, timeout 20 s) and transient (5xx, 408, 429) retry with exponential backoff and full jitter (5 s base, 15 min cap, at least `Retry-After`); 401 stops and signs out (keeping the database for the same user); a 4xx for the whole batch makes it send one mutation at a time to find the culprit; per-mutation rejections go to the failures list without blocking the rest.
- **Triggers**: launch, foreground, network regained (`expo-network`), 2 s after each local write, every 5 minutes while active, pull-to-refresh, and `expo-background-task` (WorkManager, at least every 15 min, OS-scheduled).
- **Compatibility in production** (Phase 8): the newest API runs next to older app builds and OTA bundles with pending outboxes. Migrations are additive (`migrations:check` blocks destructive ones; removals go through the two-step expand/contract of `README.md`), the protocol stays `1` with only optional additions, and the deploy workflow publishes the API before any OTA. A database restored from a backup has a lower `seq`, so devices with a newer cursor get `reset: true` and pull everything again, while their outboxes resend what the backup lost.
- No CRDT or third-party sync engine unless the simple protocol proves insufficient.

### Clients

- Both clients compute the heatmap grid via `packages/core` and render from API (web) or local DB (mobile, where `dayView`/`summarizeYear` from core build what the API's `/v1/day` and `/v1/summary` return). No duplicated date/schedule logic in app code.
- State/server cache: TanStack Query on both clients. Web routing: TanStack Router. Mobile routing: Expo Router.
- Web: PWA via `vite-plugin-pwa` (Workbox), push handled in the service worker. Styling: Tailwind v4 + shadcn/ui.
- Mobile: NativeWind, `expo-notifications`, development builds (Expo Go does not support all required push features).
- API base URL comes from env/config (`VITE_API_URL`, `EXPO_PUBLIC_API_URL`), never hardcoded. In production the web app and API share one domain (`/api/*` routed to the Worker) to avoid CORS and cookie problems.

## Design

Clean, minimal, dark-first UI. Keep the legacy palette (dark neutral background, violet accent, violet shades for heatmap intensity). The values were extracted from the legacy front (Tailwind classes) and mobile styles into `packages/design-tokens`, as canonical hex (see "Decisions"); use only tokens in app code. Light theme is optional and out of scope until requested. Mobile touch targets >= 44px; heatmap must remain legible on small screens (horizontal scroll by weeks, current week visible by default).

## Decisions

Owner decisions taken before Phase 0. They override anything above that seems to contradict them.

- **Legacy data**: the legacy `legacy/server/prisma/dev.db` (in history only) is test data only. There is no legacy data import or migration: do not create an `import-legacy` script. Phase 2 delivers a **local D1 dev seed** instead (`pnpm --filter api db:seed:local`) with sample habits and completions spread over the year, covering all heatmap intensities, streaks and the year boundary (completions in late December of the previous year and early January).
- **Timezone and dates**: the server never uses `new Date()` or `Date.now()` to decide a user's calendar day. The client sends the local date as `YYYY-MM-DD`. Any server-side "today" (date window validation, reminder cron) is computed from the user's IANA timezone in `user_settings.timezone` (default `America/Sao_Paulo`), passed explicitly as a parameter to every date function in `packages/core`. Workers run in UTC regardless of the Cloudflare account or region, and the D1 region only affects latency. The cron trigger runs every 15 minutes in UTC and converts per user. `created_at`, `updated_at` and `deleted_at` are integer UTC milliseconds.
- **Timestamps vs calendar dates**: `created_at`, `updated_at`, `deleted_at` (and other instants such as `completed_at`, `archived_at`) are integer UTC ms, read as `number` (Drizzle `integer({ mode: "number" })`, not `timestamp_ms`, which returns `Date`), so rows match the contracts without conversion. Calendar dates (`start_date`, `completions.date`) stay `YYYY-MM-DD` text.
- **Design tokens**: canonical values are **hex**. Legacy front OKLCH values (Tailwind v4) are converted to hex where needed so web and mobile are identical. The heatmap has 6 levels and, like GitHub's dark theme, more done is brighter: level 1 = violet-900 `#4C1D95` up to level 5 = violet-400 `#A78BFA` (owner decision 2026-10-10; it replaced the earlier legacy mobile mapping, where level 1 was the lightest). Green stays the success color. `packages/design-tokens` generates both configs from one source: a Tailwind v4 `@theme` CSS file (web) and a Tailwind v3 preset (mobile/NativeWind).
- **NativeWind**: v4 stable (Tailwind v3). Migrate to v5 when it leaves RC.
- **TypeScript**: 6.0.x workspace-wide (typescript-eslint requires `typescript <6.1`). Do not move to TS 7 until typescript-eslint supports it.
- **Vitest**: 4.x workspace-wide. Workers tests use `@cloudflare/vitest-plugin` (the renamed, maintained successor of the deprecated `@cloudflare/vitest-pool-workers`; peers `vitest ^4.1.0 || ^5.0.0`). If a future plugin version breaks that, pin the compatible Vitest only in `apps/api`.
- **Mobile heatmap**: GitHub layout (columns = weeks), horizontal scroll, current week visible by default, same as web.
- **Password hashing**: Password hashing is deliberately lightweight to fit the free plan's CPU limit; revisit if moving to Workers Paid (raise scrypt to the Better Auth default via the versioned rehash). Details: own scrypt hasher (`apps/api/src/auth/password.ts`, `node:crypto`) with N=2048, r=8, p=1 (~4 ms per hash in local workerd, against ~70 ms for Better Auth's default N=16384, r=16), versioned format `$scrypt$v=1$n=…,r=…,p=…$salt$key`, constant-time comparison, re-hash on a successful sign-in when the stored parameters are weaker than `CURRENT_PARAMS`. Compensated by a 16-character minimum password (`PASSWORD_MIN_LENGTH` in contracts), closed signup and rate limiting.

## Git and versioning

- **Never commit.** Do not run `git add`, `git commit`, `git push`, `git stash`, `git reset`, `git rebase`, or any other command that stages, records or rewrites history. The owner reviews the diff and commits manually. Read-only commands (`git status`, `git diff`, `git log`) are fine.
- **Never add co-authorship or attribution** of any kind: no `Co-Authored-By` trailer, no "Generated with Claude Code" line, in commit messages, PR descriptions or files.
- Commit messages follow **Conventional Commits** (semantic): `type: imperative summary`, in English, lowercase type, **never use a scope in parentheses** (write `feat: add habit heatmap`, not `feat(web): ...`), no trailing period, summary up to ~72 chars. If the area matters, mention it in the summary itself (for example `fix: handle timezone in api date window`). Types: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`, `style`, `revert`. Use `!` after the type (`feat!: ...`) or a `BREAKING CHANGE:` footer for breaking changes.
- When a phase is finished, **propose a single commit message** in that format covering everything changed in the phase (a short body may list what it includes) in your final reply, and let the owner commit. Smaller tasks outside a phase also get one message.
- **Version 2.0.0**: this rewrite is version `2.0.0` in all three apps: `apps/api`, `apps/web` and `apps/mobile` (`version` in each `package.json`, and also `expo.version` in the Expo app config for mobile). The internal `packages/*` are private and keep their own version, which does not need to follow the apps. The legacy app is the 1.x line. Do not bump the version unless asked. Tags (`v2.0.0`) are created by the owner, never by Claude.
