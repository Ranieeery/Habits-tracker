# apps/api

Hono on Cloudflare Workers. See the root `CLAUDE.md` for architecture, auth, dates and sync rules.

- Entry: `src/index.ts` exports `{ fetch, scheduled }`: `createApp({ now: () => Date.now() })` (the only place that reads the clock) and the Cron Trigger handler, which calls `runScheduled` (`src/scheduled.ts`) with `controller.scheduledTime` as "now". Outgoing requests to push services use an injected `fetch` (`createApp({ now, fetch })`, `c.var.fetch`), so tests replace them. `src/app.ts` assembles the app under `/v1`: context and CORS middleware, `GET /v1/health`, Better Auth at `/v1/auth/*`, docs at `/v1/docs` (development only), then `requireUser` and the route groups. Order matters: everything registered after `requireUser` (unknown paths included) needs a session.
- Layout:
  - `src/auth/`: `options.ts` (schema-shaping Better Auth options, shared with the CLI), `auth.ts` (`createAuth`: closed signup, rate limits, trusted origins, cookies, re-hash on sign-in), `password.ts` (lightweight versioned scrypt hasher).
  - `src/http/`: `context.ts` (`AppEnv`, `router()`, `authOf`), `errors.ts` (`ApiError` bodies, status per code, OpenAPI response helpers, the 422 validation hook), `require-user.ts`, `today.ts` (the user's day from their time zone and the injected clock).
  - `src/routes/`: one `router()` per group with `createRoute` + `.openapi()` chains (keep them chained: the RPC types come from the chain).
  - `src/repos/`: every database access of the routes. Each function takes `userId` and scopes every statement by it; handlers never query `db` directly.
  - `src/push/`: `webpush.ts` (RFC 8291 aes128gcm + RFC 8292 VAPID with Web Crypto; the JWT is signed once per push service per invocation), `expo.ts` (Expo send/receipts over fetch), `dispatch.ts` (sends one message to a user's devices with isolated failures; removes 404/410 and `DeviceNotRegistered`; stores Expo tickets; `withinFetchLimit`/`FetchBudget` keep invocations under the 50-subrequest Free limit). Never log endpoints, keys or tokens.
  - `src/cron/reminders.ts`: the reminder job (receipts first, then candidates; claims the day with `claimReminderDay` before sending; `MAX_FETCHES_PER_RUN` = 40). `src/repos/reminders.ts` holds the cron's cross-user reads (`listReminderCandidates`, `listDueTickets`), the only repo functions that are not scoped by one user; every write is.
  - `src/config.ts` (typed bindings, including `vapid` and `expoAccessToken`), `src/lib/` (`Clock`, `uuidV7`), `src/env.d.ts` (secret bindings that `wrangler types` cannot see).
- RPC type for clients: `src/app-type.ts` is exported as `api/app`, resolved to the declarations that `pnpm --filter api build:types` emits into `dist/types` (gitignored; turbo runs it before `typecheck`). Never import runtime code from it.
- Worker config: `wrangler.jsonc` (`vars`: `ENVIRONMENT`, `ALLOW_SIGNUP`, `TRUSTED_ORIGINS`; `triggers.crons`: `*/15 * * * *`). Run the cron locally under `wrangler dev` with `curl "http://localhost:8787/cdn-cgi/local/scheduled?cron=*/15+*+*+*+*&time=<ms>"`. The Worker is private (`workers_dev: false`, `preview_urls: false`): in production only the public Worker of `apps/web` reaches it, through a service binding, with the `/api` prefix already stripped. `pnpm --filter api run deploy` deploys it; run `db:migrate:remote` first when the schema changed. After editing `wrangler.jsonc`, run `pnpm --filter api cf-typegen` to regenerate `src/worker-configuration.d.ts` (generated with `--strict-vars=false`: do not edit, excluded from lint and Prettier). It also picks up the names in your local `.dev.vars`: keep only `wrangler.jsonc` bindings in the committed file (secrets belong in `src/env.d.ts`). The `Env` type comes from that file plus `src/env.d.ts`.
- Runtime is workerd with `nodejs_compat`, not Node: check any new dependency runs on Workers. `node:crypto` (scrypt) and `Buffer` are available.
- Tests: `test/*.test.ts` run inside workerd through `@cloudflare/vitest-plugin` (`vitest.config.ts`, which also sets the test bindings and a random `BETTER_AUTH_SECRET`), with their own `test/tsconfig.json`. `test/apply-migrations.ts` applies `migrations/` to the test D1 before each file; D1 data is shared between tests of a file, so call `resetDb()` in `beforeEach` (deleting users cascades to all data). `test/helpers.ts` has `makeApi(nowIso, envOverrides, { fetch })` (fixed, movable clock; optional fake fetch for push services), `createUser`, `signUp`/`signIn`, `cookieOf`/`bearerOf`. `typecheck` checks `src`, `test` and the Node-side files (`tsconfig.node.json`: `scripts/`, `drizzle.config.ts`, `vitest.config.ts`).
- Push tests: `test/push-fakes.ts` (`fakePushFetch`: Web Push endpoints and the Expo API with per-test statuses, tickets and receipts; `newVapidKeys`, `newWebPushKeys`); `test/reminders.test.ts` calls `runScheduled` directly with a chosen instant.
- Secrets: Wrangler secrets in production (`BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` = the public web origin, `OWNER_EMAIL`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, optional `EXPO_ACCESS_TOKEN`; generate VAPID keys with `pnpm --filter api vapid:generate`), `.dev.vars` locally (gitignored; copy `.dev.vars.example`). Never put secrets in `wrangler.jsonc`.

## Database

- D1 binding `DB`. `database_id` in `wrangler.jsonc` is the production database (not a secret); local D1 ignores it.
- Schema: `src/db/schema.ts` (Drizzle), which re-exports the Better Auth tables of `src/db/auth-schema.ts`. That file is generated (`pnpm --filter api auth:generate`, from `src/auth/options.ts` through `scripts/auth-cli.ts`): regenerate it instead of editing it, then run `db:generate`. `createDb(env.DB)` in `src/db/client.ts`.
- Every domain `user_id` references `user.id` with `ON DELETE CASCADE`.
- Migrations: edit the schema, run `pnpm --filter api db:generate`, review the SQL in `migrations/` and commit it with `migrations/meta/`. Never edit an applied migration; add a new one. A migration that rebuilds tables must replace drizzle-kit's `PRAGMA foreign_keys=OFF/ON` with `PRAGMA defer_foreign_keys = on` (D1 always enforces foreign keys), as `0002_user_fk.sql` does.
- `src/db/records.ts` converts between rows and contract records, parsing with `@habits/contracts` on every write and read. Do not insert rows that bypassed it.
- Instants are `number` ms (`integer({ mode: "number" })`); calendar dates are `YYYY-MM-DD` text with a CHECK (`date(x) IS x`). In SQLite CHECKs, compare with `IS` when an operand may be NULL: a NULL result passes the CHECK. Exception: Better Auth's tables use `timestamp_ms` (`Date`).
- Batches: D1 allows at most 100 bound parameters per statement; chunk multi-row inserts (see `src/db/seed/apply.ts`).

## Dev seed

`src/db/seed/`: `build.ts` (pure, deterministic for a reference `today`, fixed `DEV_USER_ID`, `DEV_USER_EMAIL`/`DEV_USER_PASSWORD`), `validate.ts` (contracts + "possible on date" checks), `apply.ts` (one batch: delete the dev user, which cascades to all their rows, then insert the auth user, its password credential, settings, habits and completions; the password hash is passed in so `build.ts` stays pure). `scripts/seed-local.ts` runs it against the local `.wrangler/state` through Wrangler's `getPlatformProxy()` and prints the sign-in. Re-seeding replaces the dev user and all their data (sessions included).
