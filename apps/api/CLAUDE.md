# apps/api

Hono on Cloudflare Workers. See the root `CLAUDE.md` for architecture, auth, dates and sync rules.

- Entry: `src/index.ts` exports `{ fetch, scheduled }`: `createApp({ now: () => Date.now() })` (the only place that reads the clock) and the Cron Trigger handler, which calls `runScheduled` (`src/scheduled.ts`) with `controller.scheduledTime` as "now". Outgoing requests to push services use an injected `fetch` (`createApp({ now, fetch })`, `c.var.fetch`), so tests replace them. `src/app.ts` assembles the app under `/v1`: the `apiHeaders` middleware (first, so every response gets `Cache-Control: no-store` and `nosniff`, see `src/http/api-headers.ts`), context and CORS middleware, `GET /v1/health`, Better Auth at `/v1/auth/*`, docs at `/v1/docs` (development only), then `requireUser` and the route groups. Order matters: everything registered after `requireUser` (unknown paths included) needs a session.
- Layout:
  - `src/auth/`: `options.ts` (schema-shaping Better Auth options, shared with the CLI), `auth.ts` (`createAuth`: closed signup, rate limits, trusted origins, cookies, re-hash on sign-in), `password.ts` (lightweight versioned scrypt hasher).
  - `src/http/`: `context.ts` (`AppEnv`, `router()`, `authOf`), `errors.ts` (`ApiError` bodies, status per code, OpenAPI response helpers, the 422 validation hook), `require-user.ts`, `today.ts` (the user's day from their time zone and the injected clock), `schedule-version.ts` (`clientScheduleVersion` from `X-Habits-Schedule-Version`, 1 when absent; `isReadableBy` filters habits of newer schedule types out of `GET /v1/habits` and the pull).
  - `src/routes/`: one `router()` per group with `createRoute` + `.openapi()` chains (keep them chained: the RPC types come from the chain).
  - `src/repos/`: every database access of the routes. Each function takes `userId` and scopes every statement by it; handlers never query `db` directly.
  - `src/push/`: `webpush.ts` (RFC 8291 aes128gcm + RFC 8292 VAPID with Web Crypto; the JWT is signed once per push service per invocation), `expo.ts` (Expo send/receipts over fetch), `dispatch.ts` (sends one message to a user's devices with isolated failures; removes 404/410 and `DeviceNotRegistered`; stores Expo tickets; `withinFetchLimit`/`FetchBudget` keep invocations under the 50-subrequest Free limit; D1 queries have their own limit of 50 per invocation on Free). Never log endpoints, keys or tokens.
  - Sync: `src/routes/sync.ts` (`POST /v1/sync/push`, `GET /v1/sync/pull`, cursor `1.<seq>` via `encodeCursor`/`decodeCursor`; rules from `applyMutation` in core) and `src/repos/sync.ts` (processed mutation lookup, record loading, the one write batch with the completion upsert on `(habit_id, date)`, the one-batch pull read, purge). `findTakenIds` is an id-only probe across users (a client cannot reuse another user's record id) and `listSyncUsers` feeds the cron's purge; everything else is scoped by user. `src/cron/sync-purge.ts`: daily purge of tombstones and applied mutation ids (first cron run after 06:00 UTC, `MAX_PURGE_USERS_PER_RUN` = 8), called by `runScheduled` after the reminders.
  - `src/cron/reminders.ts`: the notification job (receipts first, then candidates: users with a device and the reminder or the morning digest on; both time windows checked in memory, then one load of habits and today's completions, the two decisions from core, and for each kind to send a claim with `claimDigestDay`/`claimReminderDay` before sending; `MAX_FETCHES_PER_RUN` = 40; the report counts `digests` and `reminders`). `src/repos/reminders.ts` holds the cron's cross-user reads (`listReminderCandidates`, `listDueTickets`), the only repo functions that are not scoped by one user; every write is.
  - `src/config.ts` (typed bindings, including `vapid` and `expoAccessToken`), `src/lib/` (`Clock`, `uuidV7` = core's formatter with Web Crypto bytes, `log.ts`), `src/env.d.ts` (secret bindings that `wrangler types` cannot see).
  - Logging: only through `log.info/warn/error(event, fields)` from `src/lib/log.ts` (JSON objects, indexed by Workers Logs). Fields are counts, statuses, codes and `errorName(error)`; never messages that may carry data, headers, bodies, URLs with query strings, emails, tokens, push endpoints or keys. `runScheduled` logs `cron_reminders`/`cron_sync_purge`, and on failure `cron_failed` before rethrowing (the invocation shows as an exception).
  - `scripts/` (Node, type stripping): `seed-local.ts`, `generate-vapid-keys.ts`, `auth-cli.ts`, `check-migrations.ts` + `migration-guard.ts` (destructive migration check, `migrations:check`), `backup.ts` (`db:backup:local`/`db:backup:remote` into `backups/` at the repo root), `restore-prepare.ts` + `sql-dump.ts` (`db:restore:prepare`), `row-counts.sql`, `cpu-report.ts`. Pure rules (`migration-guard.ts`, `sql-dump.ts`) are tested from `test/` and must not import Node modules.
- RPC type for clients: `src/app-type.ts` is exported as `api/app`, resolved to the declarations that `pnpm --filter api build:types` emits into `dist/types` (gitignored; turbo runs it before `typecheck`). Never import runtime code from it.
- Worker config: `wrangler.jsonc` (`vars`: `ENVIRONMENT`, `ALLOW_SIGNUP`, `TRUSTED_ORIGINS`; `triggers.crons`: `*/15 * * * *`). Run the cron locally under `wrangler dev` with `curl "http://localhost:8787/cdn-cgi/local/scheduled?cron=*/15+*+*+*+*&time=<ms>"`. The Worker is private (`workers_dev: false`, `preview_urls: false`): in production only the public Worker of `apps/web` reaches it, through a service binding, with the `/api` prefix already stripped. In production the `deploy` workflow deploys it (backup, migrations, then `wrangler deploy`); by hand: `db:migrate:remote` first when the schema changed, then `pnpm --filter api run deploy`. After editing `wrangler.jsonc`, run `pnpm --filter api cf-typegen` to regenerate `src/worker-configuration.d.ts` (generated with `--strict-vars=false`: do not edit, excluded from lint and Prettier). It also picks up the names in your local `.dev.vars`: keep only `wrangler.jsonc` bindings in the committed file (secrets belong in `src/env.d.ts`). The `Env` type comes from that file plus `src/env.d.ts`.
- Runtime is workerd with `nodejs_compat`, not Node: check any new dependency runs on Workers. `node:crypto` (scrypt) and `Buffer` are available.
- Tests: `test/*.test.ts` run inside workerd through `@cloudflare/vitest-plugin` (`vitest.config.ts`, which also sets the test bindings and a random `BETTER_AUTH_SECRET`), with their own `test/tsconfig.json`. `test/apply-migrations.ts` applies `migrations/` to the test D1 before each file; D1 data is shared between tests of a file, so call `resetDb()` in `beforeEach` (deleting users cascades to all data). `test/helpers.ts` has `makeApi(nowIso, envOverrides, { fetch })` (fixed, movable clock; optional fake fetch for push services), `createUser`, `signUp`/`signIn`, `cookieOf`/`bearerOf`. `typecheck` checks `src`, `test` and the Node-side files (`tsconfig.node.json`: `scripts/`, `drizzle.config.ts`, `vitest.config.ts`).
- Ops tests: `test/api-headers.test.ts` (no-store on every kind of response), `test/migration-guard.test.ts` (rules, plus every committed migration passes), `test/sql-dump.test.ts` (statement splitting and restore order).
- 2.3.0 window (30 days): `test/completions.test.ts` (−30/−31 and +1/+2 at the São Paulo midnight, past-day tombstone, another user's habit) and `test/sync.test.ts` (`completion.set` at −30 applied, −31 rejected).
- Habit order tests: `test/habit-order.test.ts` (keys on create, PATCH and sync, list order with empty keys last, and the `0006` backfill re-run from `env.TEST_MIGRATIONS`, including the `server_seq` bump).
- Sync tests: `test/sync.test.ts` (idempotency, natural-key upsert, paging with writes in between, scope, rejections, batch limits, purge, and the `0004` backfill re-run from `env.TEST_MIGRATIONS`).
- 2.2.0 tests: `test/schedules.test.ts` (new schedule types over REST, date rules, day views with mixed types, the filter for clients without the version header, paging past hidden rows), `test/digest.test.ts` (digest at 09:00, once a day under overlapping runs, the window, hidden titles, independent of the reminder, devices failing), `test/migration-0005.test.ts` (defaults and the rounding `UPDATE` re-run from `env.TEST_MIGRATIONS`, tolerant settings reads).
- Push tests: `test/push-fakes.ts` (`fakePushFetch`: Web Push endpoints and the Expo API with per-test statuses, tickets and receipts; `newVapidKeys`, `newWebPushKeys`); `test/reminders.test.ts` calls `runScheduled` directly with a chosen instant.
- Secrets: Wrangler secrets in production (`BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` = the public web origin, `OWNER_EMAIL`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, optional `EXPO_ACCESS_TOKEN`; generate VAPID keys with `pnpm --filter api vapid:generate`), `.dev.vars` locally (gitignored; copy `.dev.vars.example`). Never put secrets in `wrangler.jsonc`.

## Database

- D1 binding `DB`. `database_id` in `wrangler.jsonc` is the production database (not a secret); local D1 ignores it.
- Schema: `src/db/schema.ts` (Drizzle), which re-exports the Better Auth tables of `src/db/auth-schema.ts`. That file is generated (`pnpm --filter api auth:generate`, from `src/auth/options.ts` through `scripts/auth-cli.ts`): regenerate it instead of editing it, then run `db:generate`. `createDb(env.DB)` in `src/db/client.ts`.
- Every domain `user_id` references `user.id` with `ON DELETE CASCADE`.
- Migrations: edit the schema, run `pnpm --filter api db:generate`, review the SQL in `migrations/` and commit it with `migrations/meta/`. Never edit an applied migration; add a new one. Migrations must be additive: production runs them while the previous API version and older mobile builds (with pending outboxes) keep working, and a Worker rollback never undoes them. `pnpm --filter api migrations:check` (CI) fails on `DROP`, `ALTER TABLE … RENAME` and `DELETE FROM` unless the file has a `-- migration-guard: destructive-ok <reason>` line, added only for the approved "contract" step of a two-step change (`README.md`). A migration that rebuilds tables must replace drizzle-kit's `PRAGMA foreign_keys=OFF/ON` with `PRAGMA defer_foreign_keys = on` (D1 always enforces foreign keys), as `0002_user_fk.sql` does.
- `src/db/records.ts` converts between rows and contract records, parsing with `@habits/contracts` on every write and read (dropping `server_seq`). Do not insert rows that bypassed it.
- `server_seq` on `habits` and `completions` is written only by the triggers of `0004_sync.sql` (`AFTER INSERT` and `AFTER UPDATE OF` every other column: take `sync_state.seq + 1`). Never set it from code. The update triggers list their columns (`AFTER UPDATE OF …`): a column added later (like `habits.sort_key`, 2.4.0) is not in the list, so every write of it must also set `updated_at` (as `changedHabitFields` does), and a backfill that sets only that column must add `updated_at = updated_at` (see `0006_habit_order.sql`). drizzle-kit does not know about triggers or data backfills: they were appended by hand to the generated `0004_sync.sql`, and any future rebuild of these tables must recreate the triggers. Inside a trigger, the firing statement's conflict clause overrides the trigger's own (`INSERT OR IGNORE` in a trigger fired by an upsert still fails), so the triggers create the `sync_state` row with `INSERT … SELECT … WHERE NOT EXISTS`. Wrangler's SQL splitter (migrations apply and `readD1Migrations` in tests) handles `CREATE TRIGGER … BEGIN … END`.
- Instants are `number` ms (`integer({ mode: "number" })`); calendar dates are `YYYY-MM-DD` text with a CHECK (`date(x) IS x`). In SQLite CHECKs, compare with `IS` when an operand may be NULL: a NULL result passes the CHECK. Exception: Better Auth's tables use `timestamp_ms` (`Date`).
- Batches: D1 allows at most 100 bound parameters per statement; chunk multi-row inserts and `IN` lists with `chunk`/`columnCount` from `src/db/chunk.ts` (Drizzle binds every column of a multi-row insert, defaults like `server_seq` included). The Free plan also allows 50 D1 queries per invocation; count each statement of a batch.

## Dev seed

`src/db/seed/`: `build.ts` (pure, deterministic for a reference `today`, fixed `DEV_USER_ID`, `DEV_USER_EMAIL`/`DEV_USER_PASSWORD`), `validate.ts` (contracts with strict schedules + "possible on date" checks); the seed also creates one habit of each 2.2.0 type starting on the reference day (no completions, so the past heatmap stays the same), `apply.ts` (one batch: delete the dev user, which cascades to all their rows, then insert the auth user, its password credential, settings, habits and completions; the password hash is passed in so `build.ts` stays pure). `scripts/seed-local.ts` runs it against the local `.wrangler/state` through Wrangler's `getPlatformProxy()` and prints the sign-in. Re-seeding replaces the dev user and all their data (sessions included).
